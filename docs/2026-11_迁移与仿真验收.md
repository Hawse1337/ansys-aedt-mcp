# AEDT MCP 跨机迁移与仿真验收补充（2026-11-02）

本文件优先于旧章节中与之冲突的建议；旧案例为历史观察而非跨版本保证。适用验证基线：Windows、本机AEDT 2026 R1、PyAEDT 1.9.0及本套件manifest中指定的旧版上游文件。不同AEDT/MCP版本，先查实际源码及hash，禁止用--force覆盖新机器已有工作。

## 1. 新电脑部署顺序

1. 先单独安装并启动兼容的AEDT/HFSS与许可，不启动求解，确认版本；Python虚拟环境中核对`python -m pip show pyaedt mcp`。本套件是**补丁**，不是完整AEDT或完整MCP仓库。
2. 定位目标MCP仓库，完整复制仓库、pyproject、虚拟环境清单；用git status/diff记录用户已有改动。停在此处由用户确认后续写入。完整查看manifest的upstream_base_commit、各源/目标hash和代码diff。hash mismatch=版本不兼容或有本地改动，必须手工合并/审查，不要--force。
3. 用目标虚拟环境运行 `python install.py --check --tests --repo <绝对仓库路径>`。初次未安装guard时测试可能失败：这是预检信息，不是忽略版本差异的理由。审查无误后才按README安装；安装器验证包内payload哈希并在失败时非零退出；安装非事务化，失败可能留下部分写入，需对照明确备份手动恢复。自动--revert已禁用，因为历史实现会混合批次。
4. `mcp<2`与pyaedt==1.9.0是旧仓库经过测试的兼容示例，不应不经检查地套到新版MCP。客户端超时、服务端worker超时、求解器异步任务是三层独立预算；修改服务启动环境后需重启明确的MCP服务并验证工具schema、PID/端口及握手，不能因客户端超时认为求解已停止。
5. 用全新、明确命名且无用户数据的项目测试连接、创建、保存、重新打开、原生读回和小求解；不要用现有用户工程做破坏性探针。用户工程迁移先备份 `.aedt` 与同名 `.aedtresults` 全目录，核对哈希并在目标机试开副本。
6. 端口/PID必须唯一指定。发现多个进程先列会话；不要按进程名全杀、自动关闭用户项目或删除锁。锁冲突、Save错误、文件丢失立即停止写入并报告，核查所有者、时间戳及备份。若此前发生事故必须如实说明。

## 2. 守卫与安装器的边界

- v1.3守卫在`AEDT_GUARD_ATTACH_OPEN=1`且名字无法从已知路径解析时**拒绝**，不再假设该工程已打开。此改动会破坏依赖不安全绕行的旧脚本，应改为先针对明确desktop只读发现项目绝对路径，再显式打开/附着。确认路径、design、结果所属会话。
- 守卫是防误操作辅助，并非事务锁、并发防护或备份。绝对路径、相对带分隔符路径、未安装守卫的独立脚本及并发创建仍存在风险；`create_project`的exists检查并非原子操作。只在隔离工作目录新建且检查目标不存在，保留回滚。
- 默认搜索路径含旧机器路径；新机明确设置 `AEDT_GUARD_SEARCH_DIRS`，不可依赖旧用户目录。重名项目时更应传已核实的绝对路径，避免搜索顺序误指。
- 代码补丁仅有旧upstream基线hash；新一代不同MCP可能已解决问题或结构不同。不要直接覆盖，先查manifest、源码和测试。仓库、MCP客户端与AEDT不等同；客户端超时配置应按实际配置schema验证。

## 3. HFSS求解与证据合同

- 定义几何、端口/材料/求解域、无限球、网格、独立setup；作原生设计验证。所有改变在独立副本，附精确manifest；不要将后处理球或结果自动修改保存回用户原工程。
- 原生设置 `UseIterativeSolver=True`；不要相信会被EditSetup丢弃的`DrivenSolverType`别名或PyAEDT缓存，读取 `GetChildObject('Analysis').GetChildObject(name).GetPropValue('Solver Type')` 和 `Solution Freq`。先小案例验证实际API适用性。
- 本项目测试中 `h.odesign.Analyze(name, False)` 只提交了一次自适应；使用已验证的 `h.analyze(setup=name, cores=2, tasks=1, use_auto_settings=False)` 或已验证的MCP入口。PyAEDT analyze可能先save；按项目保护协议事先备份/确认。对Icepak或其他求解器不要套用HFSS结论；MCP工具自带的求解器专用警示必须遵循。
- 每个重要频点独立setup。实际结果频率、端口参考阻抗/归一化、实虚频率轴必须一致；`full_matrix_real_imag[0]`及`[1]`分别是实数与虚数表，每行常为 `[frequency,value]`，先校验shape/频率再构造复数。
- 原生分析返回True、正常完成、已有LastAdaptive、桌面空闲、最多5/8步都**不是**收敛证明。保存原生profile和convergence，检查实际求解身份、最终ΔS和连续合格次数。曾见26.79GHz五步正常完成，但仅最后1步达标，要求连续2步，故未收敛。
- 失败/异常不评分、不覆盖旧结果；审查license、错误消息、profile、资源后决定重试。不要自动删除setup、清网格或重复无界求解；明确CPU核数与单任务，128GB不是无限资源。

## 4. 扫频、远场和优化

- 24–30GHz在独立馈源F28网格上成功：61输出点，实际7个插值基频，约16分38秒、峰值约12GB；24–36GHz 121输出点、11个基频约11分54秒，原生插值收敛。输出点不等于独立自适应点；应对关键带端/共振/阈值用独立网格核验。
- 24–36GHz独立馈源中24/30/32.2/36GHz独立收敛S11约−12.55/−13.59/−10.12/−7.52dB。32.2只有0.12dB余量；24是扫描边界不是低端截止。不能声称24–36全部达标，不能将独立馈源带宽直接转移到带盘天线。
- 分清 `DirectivityTotal`、`GainTotal` 与 `RealizedGainTotal`，同频、同极化、同归一化比较PPT；匹配好不意味着高增益。方位需报告最小值、线性功率平均值、最大−最小起伏，而非只报告全空间峰值。
- 功率闭合、球面积分、0/360°接缝、极点及网格/边界独立性均需审计。原生Prad/Pacc>1为数值异常，不能报告效率超过100%或裁剪。30GHz独立馈源球积分相对原生辐射功率差约1.39%，角步1°仍存在；不应归咎角采样或声称物理验证完成，功率单位空字符串也必须明确标记。
- 扫参先单变量、小样本，保留精确参数、网格、原始结果、失败日志、独立频点收敛证据。2026-10-28候选筛选脚本未导出收敛/原始复矩阵、未断言频率身份，相关数字是未审计筛选，不得称验证最优；1.625失败原因记录不足，不得编造为资源问题。
- GA只在稳定评价链路+可行性约束明确后启动；优先带内最差S11、方位最小/功率平均实现增益和最大起伏。失败候选不计分；单频高峰值或低起伏不代表宽带性能。原始工程、用户GUI与旧结果受保护。
